# Early-stage startup preparation

## What this label tells you

Use early stage as a question about operating context: small team, uncertain product requirements or a broad role may be relevant, but establish each from the actual posting and conversation. This chapter does not assign any catalog company a current funding round or prescribe one startup interview sequence.

[OFFICIAL; HISTORICAL] Harj Taggar's September 7, 2018 YC essay gives founder-side hiring advice and an example process. It is historical advice, not a 2026 requirement for YC companies or evidence of a current universal loop. [Essay](https://www.ycombinator.com/blog/convincing-engineers-to-join-your-team).

## What to establish before preparing

| Question | How it changes preparation |
|---|---|
| What would I own in the first useful delivery? | Select a project that demonstrates comparable responsibility |
| Who reviews design/code and supports an early-career engineer? | Clarifies mentorship and decision boundaries |
| Is the assessment coding, debugging, project discussion or a work trial? | Determines the practice format |
| Which resources and AI tools are allowed per stage? | Prevents carrying preparation habits into a restricted assessment |
| What are time budget, evaluation criteria and submission handling? | Makes a practical exercise bounded and reviewable |
| What user and data constraints matter? | Guides architecture and validation rather than technology guessing |

These are [INFERRED] discovery questions. A “founding engineer” title alone does not prove autonomy, compensation structure, experience requirements or an abbreviated interview.

## Preparation from fundamentals

Prepare a small end-to-end feature you can explain: input validation, an API contract, authorized persistence, one failure path, tests and a clear scope boundary. Rehearse why a simple design is adequate and what evidence would justify more infrastructure. Keep DSA fluency unless the exact process establishes a different focus.

For a 0–2-year candidate, explain personal contributions accurately. A personal project can show implementation judgment without being described as an enterprise deployment. Ask what technical support and review exist rather than assuming rapid learning will replace all supervision.

## Worked scenario

A hypothetical team asks for a document assistant “by next week.” Clarify the user's actual task, permitted documents, success criteria, whether answers need citations and what actions are allowed. Propose a bounded read-only prototype with an evaluation fixture, then list what remains unverified. Do not commit to a deadline without stating access/data/existing-code assumptions.

## Practice — STAGE-P4-01

**Intermediate; full-stack/AI/SDE; company-neutral discovery/design practice; 0–2 years.** Explain the smallest useful implementation and how you would demonstrate correctness.

<details><summary>Expected reasoning, followup and common mistake</summary>

Define a user journey, acceptance criteria, authorized data, simple architecture, a test fixture and one failure/recovery flow. Distinguish demonstration from production evidence. Followup: what would you defer and who agrees? Common mistake: selecting an agent framework before establishing the need or implying every early-stage employer uses a take-home.

</details>
