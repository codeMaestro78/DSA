## Original preparation exercises

All prompts below are **[INFERRED], company-neutral** exercises selected for this preparation path. They are not reported Palantir questions. Suggested target: early-career software/AI candidate; practice context: coding, design or project discussion, adjusted to the actual role. Difficulty: Intermediate, with advanced failure/concurrency followups optional.

1. Read an unfamiliar small codebase, explain its state model and repair one failing behavior.
2. Turn a vague operational-data request into a bounded schema/API prototype with explicit acceptance and handoff criteria.

**Exercise-specific review:**

1. Trace the unfamiliar code’s state and failing input before editing. Keep the repair local to the violated contract and show the exact regression check; do not invent a current employer debugging format.
2. Discovery should identify the user decision, authoritative data, permission owner and acceptance test. A read-only bounded prototype can be useful while live write/connector authority remains unresolved.

A strong response learns from evidence, asks useful questions and traces the user outcome. It does not invent a deployment or treat confident decomposition prose as proof of correctness.

Ask a followup that changes an assumption: input size, duplicate delivery, permission revocation, concurrent update or dependency failure. The candidate should revisit the reasoning rather than patch a memorized solution. Record hints and whether code was actually executed; a plausible explanation is not a passed runtime check.

Common mistakes: skipping the contract, omitting a failing boundary, reporting unsupported metrics, or claiming the drill is a confirmed company question.
