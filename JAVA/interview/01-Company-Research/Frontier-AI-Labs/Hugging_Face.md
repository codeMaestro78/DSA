## Role-specific preparation interpretation

All advice below is **[INFERRED]**, informed by the public product ecosystem rather than a confirmed hiring rubric:

| Target | Useful practice | Evidence limit |
|---|---|---|
| ML/library engineer | Python, tensor interfaces, tests and compatibility | A merged change or reproduction is stronger than naming a library |
| Backend/platform | Artifact/version ownership, APIs and access control | A demo upload does not establish reliable storage/serving |
| Full-stack | UI state, streaming, errors and integration | A screenshot is not an end-to-end correctness check |

## Preparation plan

[INFERRED] Must prepare a correct coding task, clear tests and an honest explanation of one contribution. Important for library/community work: reproduce an issue, isolate a minimal failing case, explain compatibility and communicate a scoped fix. Advanced GPU/distributed material should follow actual responsibilities rather than replace basic debugging skill.

**Original drill — HF-P4-01, Intermediate; company-neutral library-engineering practice:** a model-loading utility works on your fixture but breaks an older supported configuration. Explain how you would investigate and propose a compatible fix.

<details><summary>Expected reasoning and followups</summary>

Specify supported versions/input contracts, create a minimal reproduction, distinguish parser/schema/runtime failure and add a focused regression. Preserve existing behavior or make a deliberate documented compatibility decision. Followups: test matrix, unclear issue reports and how to review generated code. Weak answer: solving only the newest example or claiming community adoption from one accepted test.

</details>

## Behavioral and recruiter preparation
