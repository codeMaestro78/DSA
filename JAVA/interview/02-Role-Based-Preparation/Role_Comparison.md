# Comparing software, AI, ML and customer engineering roles

## Titles are a starting point

Responsibilities, seniority and assessment vary by employer and requisition. The table is original **[INFERRED]** curriculum guidance, not a universal job taxonomy or verified interview loop. Read the exact posting and ask which skills are assessed. A research title can overlap engineering, and an “AI engineer” can build applications, training systems or both.

| Role family | Core work to investigate in the posting | Strong preparation evidence | Common wrong assumption |
|---|---|---|---|
| SDE/backend | Reliable software, APIs, data and components | Correct implementation, tests, concurrency/data reasoning | Every software role has the same design depth |
| Applied AI engineer | Model-assisted product flows, tools/retrieval and evaluation | A bounded application with measured quality and failure analysis | Invoking a model API proves ML training expertise |
| Full-stack AI engineer | User-facing product plus backend/AI boundaries | Request lifecycle, auth, streaming, data ownership and evaluated output | A chat UI alone establishes the full system |
| RAG/search engineer | Ingestion, relevance, ranking and source lifecycle | Labeled retrieval evaluation, provenance and permission checks | A vector-store integration proves retrieval quality |
| ML engineer | Data/experiments, model training and/or serving systems | Leakage-free baseline, reproducible experiment and deployment reasoning | Every ML role is model research, or every AI role trains models |
| Applied scientist | Applied modeling, hypotheses and experiments, varying by organization | Appropriate mathematics, experimental design and domain evaluation | The title has identical degree/publication rules everywhere |
| Research engineer | Implementing/evaluating research ideas and enabling experiments | Paper reproduction, reliable experiment code and clear ablations | Only software or only mathematics matters |
| Research scientist | Developing and testing novel hypotheses/methods | Research reasoning, evidence and contributions relevant to the team | A paper count alone determines readiness |
| FDE/customer engineering | Customer discovery, implementation, integration and delivery | A real integration plus clear scope, acceptance and handoff evidence | Customer-facing work is only presentations or a fixed interview format |
| Data/MLOps/platform | Data correctness; model lifecycle; runtime/reliability respectively | Backfill/data contract; version/rollback; incident/capacity reasoning | The three titles are interchangeable |

## Choose an early-career preparation path

[INFERRED] Keep backend/SDE correctness as the shared core, choose applied AI or full-stack AI as the primary extension, and retain ML/statistics fundamentals. Choose a deeper ML/research path when the role and your diagnostics justify the additional mathematics/experimentation work. FDE skills can be practiced through honest discovery and integration scenarios without claiming enterprise customer experience.

For one real posting, label each required skill as demonstrated, adjacent or unassessed. Attach an artifact or observed result to “demonstrated.” Select the weakest important prerequisite for the next practice session. Do not mark a skill demonstrated because a chapter was read or a framework appeared in a dependency list.

## Practice

**ROLE-P3-01 — Beginner/Intermediate; company-neutral; role-selection/project discussion; approximately 0–2 years.** Compare an applied AI product role with a research-engineering role using actual responsibilities. What evidence can you offer now, and what is the next gap?

<details><summary>Expected reasoning and followup</summary>

An applied product example should explain application contracts, quality evaluation and operational boundaries. A research-engineering example should explain implementation of an experimental idea, baseline, reproducibility and failure analysis. Roles overlap; the posting determines emphasis. State real evidence and limitations instead of inventing experience or treating titles as fixed categories.

Followup: Which skill is shared, and which requires a different next exercise? Common mistake: ranking titles by prestige instead of matching actual work and readiness.

</details>
