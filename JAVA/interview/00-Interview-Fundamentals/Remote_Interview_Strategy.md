# Remote interview strategy

## Establish the actual rules

Check time zone, meeting URL, editor, code execution, documentation access, AI assistance and any recording policy in the invitation. Permission to use documentation does not imply permission to use generative AI. Company policies can differ by assessment; follow the current instructions for that task.

For published examples and uncertainty, use [the company evidence briefs](../01-Company-Research/README.md). This chapter's equipment and recovery checklist is [INFERRED] preparation advice, not a universal employer requirement.

## Rehearse the complete setup

Use the same device, browser, keyboard layout and audio arrangement you expect to use. Open a harmless sample file and verify that you can share the intended window, type, compile/run if permitted and draw a simple diagram. Increase text size enough for both sides to read. Share the smallest necessary window and close unrelated sensitive material.

Keep an alternate contact route from the invitation. If a connection drops, rejoin or follow the supplied contact instructions. Do not assume the interviewer can see an update until confirmed. If the editor loses state, describe what happened and reconstruct from the last confirmed point instead of pretending the work was preserved.

## Working without your usual IDE

Practice basic language syntax, common collections, function signatures and a small test harness. If execution is unavailable, trace a minimal example carefully and state that the code has not been run. A manual trace is useful evidence but cannot be reported as compilation.

When using a drawing tool, label boxes with responsibilities rather than vendor names alone. Explain what data crosses each arrow. Confirm whether the interviewer wants a high-level flow or a deeper API/schema view.

## Accessibility and interruptions

Ask the recruiter about necessary accommodations before the assessment when possible. Agree how you will signal an audio problem or ask for a question to be repeated. Repeating a misunderstood question is better than answering a different one. Do not disclose more personal information than is necessary for the request.

## Practice scenario

Ten minutes into a task, code execution stops working. What do you do?

<details><summary>Expected reasoning</summary>

Tell the interviewer, confirm whether to continue manually or switch tools, preserve the latest code if possible, and distinguish unexecuted changes from previously checked work. Do not move to an unapproved environment or use prohibited tools without permission.

</details>

## Checklist

- [ ] Time zone, access and task permissions checked.
- [ ] Audio/share/editor rehearsed.
- [ ] Recovery contact and accessibility needs handled.
- [ ] Testing claims reflect what actually ran.
