# Recruiter screen

## Purpose and boundary

A recruiter discussion helps both sides establish whether the opportunity fits. It may cover background, motivation, logistics and the later process. Do not assume it is purely administrative or secretly a standardized coding round. Confirm the invitation's scope.

## A useful introduction

[INFERRED] Aim for an initial 45–60 second explanation, then allow questions. This is a rehearsal budget:

“I am an early-career engineer focused on [actual strengths]. In [real project/work], I personally built [specific contribution]. I learned [concrete lesson]. I am interested in this role because [responsibility from the posting] connects to that experience and [credible next step].”

Do not say “expert in ML” merely because you used a model API. State what you implemented and what remains unfamiliar. Academic, open-source and personal work can provide evidence when paid experience is limited; identify the context honestly.

## Questions that change preparation

| Ask | Why it matters |
|---|---|
| Which level/team and responsibilities apply? | The same title can hide different expectations |
| What are the stages and evaluated skills? | Determines practice allocation |
| Which language/editor and can code execute? | Determines environment rehearsal |
| Which references and AI tools are permitted in each task? | Permissions can differ by stage |
| Is a take-home expected, and what is its scope/time budget? | Helps set a concrete work boundary |
| What is the location/work-authorization requirement? | Avoids preparing for an ineligible requisition |
| What timeline and accommodations process apply? | Makes logistics explicit |

Ask about compensation scope when relevant; do not fabricate competing offers or current pay. Employment and compensation rules depend on jurisdiction, so this chapter provides communication practice, not legal advice.

## Handle an experience gap

If asked about production Kubernetes and you have only local Docker experience, say so. Explain the adjacent evidence you do have, then ask how central cluster operations are to the role. A truthful boundary is more useful than a claim that collapses under followup.

## Practice

Answer “Why this role?” using one actual posting and one true project contribution. Then answer “What have you not done yet?” without apologizing for every gap.

<details><summary>Review criteria</summary>

A strong answer connects a responsibility to evidence, names the scope of your work and shows an informed learning direction. Weak answers repeat company branding, recite the whole resume, or claim familiarity with every technology without an example.

</details>
